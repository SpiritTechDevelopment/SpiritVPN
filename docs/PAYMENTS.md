# Архитектура биллинга и выдачи VPN

Подсистема биллинга и управления доступом `SpiritVPN` спроектирована по принципам Domain-Driven Design (DDD) с четким разделением ответственности между приемом средств и выдачей услуг.

## Жизненный цикл платежа и выдачи доступа

Весь процесс от получения денег до включения интернета проходит полностью автоматически:

1. **Прием Webhook'а (API Layer)**
   * Внешний шлюз (например, Cryptomus) отправляет HTTP POST запрос об успешной оплате.
   * Контроллер Gin принимает запрос и передает его в `Payment Service`.

2. **Валидация и защита (Payment Provider)**
   * Система проверяет криптографическую подпись (MD5 хеш) для защиты от возможных фейк запросов.
   * Формат ответа приводится к единому стандарту `WebhookPayload`.

3. **Транзакция БД (Service Layer)**
   * Открывается SQL-транзакция.
   * Используется **Row-level lock** (`FOR UPDATE`), который блокирует строку платежа. Это гарантирует, что при дублировании вебхуков система не начислит подписку дважды.
   * Статус платежа меняется с `pending` на `succeeded`.

4. **Выдача доступа (VPN Manager)**
   * Асинхронно запускается `vpn.Manager`.
   * **Поиск подписки:** Если у юзера есть активная подписка, ее `end_date` продлевается на срок тарифа. Если нет — создается новая.
   * **Балансировка:** База находит VPN-сервер с наименьшим `load_percent` (процентом загрузки) и привязывает пользователя к нему.
   * **Генерация конфига:** Генерируется уникальный `UUID` для VLESS.
   
5. **Интеграция с ядром (Xray gRPC)**
   * Менеджер отправляет gRPC запрос `AddUser` напрямую в работающее ядро Xray.
   * Доступ активируется мгновенно, **без перезагрузки VPN-сервера**.

## Структура модулей

* `internal/payments/provider.go` — абстрактные интерфейсы. Позволяют легко менять платежные шлюзы (Cryptomus, YooKassa) без изменения бизнес-логики.
* `internal/payments/service.go` — бизнес-логика транзакций и защита от гонок (Race Conditions).
* `internal/vpn/manager.go` — оркестратор. Связывает базу данных подписок с реальным Xray-клиентом.
