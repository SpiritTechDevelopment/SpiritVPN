# База данных

PostgreSQL 14. Всё состояние backend живёт здесь; в памяти процесса не хранится
ничего, что нельзя потерять при перезапуске.

## Как устроена работа со схемой

ORM нет. Схема задаётся versioned SQL-миграциями, запросы пишутся вручную, код
доступа к ним генерируется.

* **Миграции** — `internal/migrations`, поверх golang-migrate. Файлы встроены в
  бинарник через `embed`. Накатывает их команда `migrate`, это шаг деплоя перед
  rollout; приложение схему не меняет и при старте не трогает.
* **Запросы** — `internal/postgres/queries/*.sql`. По ним sqlc генерирует
  `internal/postgres/db`. Каталог правится только перегенерацией:
  `go tool sqlc generate`.
* **Драйвер** — pgx. Транзакциями владеют адаптеры в `internal/postgres`, порядок
  шагов внутри транзакции задают use case'ы в `internal/app`.

## Соглашения

* Временные метки: `timestamptz` в UTC.
* `uint64` с провода (счётчики байтов, `command_number`, порядковые номера
  порций трафика, байты квоты) хранится как `numeric(20,0)`. Внутренние счётчики
  backend — `bigint`.
* Перечислимые значения: `text` с `CHECK`. Нативный `ENUM` не используется, чтобы
  набор значений менялся обычными миграциями.
* `ON DELETE CASCADE` не используется нигде. Историю backend не удаляет.

Таблиц пятнадцать, пятью группами.

### Признаки неактуальности

У каждой группы таблиц свой признак.

| признак | где | означает |
|---|---|---|
| `current = false` | таблицы топологии | объект отсутствует в последнем снимке манифеста |
| `retired_at IS NOT NULL` | `vpn_accesses` | доступ отозван, не выдаётся и не восстанавливается |
| `closed_at IS NOT NULL` | `quota_periods` | период учёта закрыт, начисления идут в следующий |
| `exhausted_at IS NOT NULL` | `node_quota_usage` | квота на ноде исчерпана, доступ там заблокирован |

Строки при этом остаются. Единственное настоящее удаление в схеме — уборка в
реестре дедупликации трафика.

### Аренда задач воркерами

Пара колонок `lease_owner` / `lease_expires_at` есть в `agent_operations`,
`manifest_materialization_jobs`, `node_usage_cursors` и `vpn_nodes` (там она
названа `reconcile_lease_*`). Воркер захватывает строку, проставляя себя
владельцем и момент истечения, по завершении шага освобождает. Упавший процесс
оставляет захват, который истечёт сам. Отдельной таблицы блокировок нет.

## Топология

Эти пять таблиц — **проекция** infrastructure manifest: не источник истины, а
копия того, что приехало в последнем снимке. Backend переносит сюда содержимое принятого снимка.

### manifest_revisions

Журнал принятых снимков.

| колонка | тип | что означает |
|---|---|---|
| `revision` | `bigint` PK | глобальная, строго возрастающая; монотонность проверяет приложение |
| `digest` | `text` | канонический отпечаток содержимого; отличает идемпотентный повтор от конфликтующего снимка с той же `revision` |
| `canonical_payload` | `jsonb` | сам снимок в каноническом виде |
| `applied_at` | `timestamptz` | когда снимок принят |

Пишут: `ApplyFleetManifest`.
Читают: `ApplyFleetManifest`, `stats`.

На `revision` ссылаются все таблицы топологии: по ней видно, в каком снимке
объект встречался последний раз.

### vpn_fleets

| колонка | тип | что означает |
|---|---|---|
| `vpn_fleet_id` | `bigint` PK | принятый идентификатор не удаляется и не переиспользуется |
| `manifest_revision` | `bigint` | ревизия, в которой флот виден последний раз |
| `current` | `boolean` | присутствует ли в последнем снимке |
| `created_at`, `updated_at` | `timestamptz` | когда флот принят и когда строка менялась |

Пишут: `ApplyFleetManifest`.
Читают: `ApplyCustomerAccess`, `ApplyFleetManifest`.

Флот может быть пустым, без нод и связей, но обязан присутствовать в каждом
последующем снимке.

### vpn_nodes

Проекция манифеста плюс состояние сверки. Второе живёт здесь же, а не отдельной
таблицей: это счётчики одной ноды, и запись манифеста их не затрагивает — она
перечисляет свои колонки явно.

| колонка | тип | что означает |
|---|---|---|
| `node_id` | `text` PK | стабильная идентичность; строка заводится навсегда |
| `agent_config` | `jsonb` | endpoint агента, TLS SNI, ожидаемая identity сертификата; клиенту не показывается |
| `public_config` | `jsonb` | публичные REALITY/VLESS-параметры, из которых собирается ссылка |
| `desired_revision` | `bigint` | счётчик желаемого набора пользователей ноды; растёт на единицу за изменяющую транзакцию |
| `reconciled_revision` | `bigint` | последняя `desired_revision`, подтверждённая агентом полным набором; `0` — не сверялся ни разу |
| `needs_bootstrap` | `boolean` | у агента пустое или повреждённое локальное состояние; пока он не получил полный набор, удалять пользователей ему запрещено |
| `reconciled_at` | `timestamptz` | время последней принятой сверки |
| `reconcile_attempted_at` | `timestamptz` | время последней попытки |
| `reconcile_lease_owner`, `reconcile_lease_expires_at` | `text`, `timestamptz` | аренда сверки |
| `manifest_revision`, `current` | `bigint`, `boolean` | проекция манифеста |
| `created_at`, `updated_at` | `timestamptz` | когда нода принята и когда строка менялась |

Пишут: `ApplyFleetManifest` (проекцию), `reconcile` (состояние сверки),
`ApplyCustomerAccess`, `materialize`, `expiry`, `usage` (`desired_revision`).
Читают: `dispatch`, `usage`, `GetCustomerAccessLinks`, `ApplyFleetManifest`,
`materialize`, `stats`.

Отставание `reconciled_revision` от `desired_revision` показывает, насколько
состав пользователей на ноде разошёлся с тем, каким его хочет видеть backend.
Равенство означает, что агент подтвердил полный набор именно этой версии.

Темп сверки задаётся `reconcile_attempted_at`, а не временем успеха: у ноды, где
сверка стабильно не удаётся, пауз бы не было.

### vpn_fleet_nodes

Состав флотов: какая нода в каком флоте.

| колонка | тип | что означает |
|---|---|---|
| `vpn_fleet_id`, `node_id` | `bigint`, `text` | составной первичный ключ |
| `manifest_revision`, `current` | `bigint`, `boolean` | `current = false` означает, что нода покинула флот |

Пишут: `ApplyFleetManifest`.
Читают: `ApplyCustomerAccess`, `ApplyFleetManifest`, `GetCustomerAccessLinks`.

### vpn_bridge_routes

Направленные связи entry → exit.

| колонка | тип | что означает |
|---|---|---|
| `vpn_fleet_id`, `routing_key` | `bigint`, `text` | составной первичный ключ; `routing_key` — стабильная идентичность связи внутри флота |
| `entry_node_id` | `text` | нода, на которую ставится пользователь; `CHECK` запрещает совпадение с exit |
| `exit_node_id` | `text` | нода выхода |
| `egress_tag` | `text` | тег Xray outbound на входной ноде, непустой; уходит агенту дословно как `egress_key` |
| `display_name` | `text` | человекочитаемое имя во фрагменте VLESS-ссылки |
| `manifest_revision`, `current` | `bigint`, `boolean` | в каком снимке связь видна последний раз и действует ли сейчас |

Пишут: `ApplyFleetManifest`.
Читают: `ApplyCustomerAccess`, `GetCustomerAccessLinks`, `ApplyFleetManifest`.

Пара `(entry, exit)` уникальна среди действующих связей флота и неизменяема для
существующего `routing_key`.

## Доступ

Здесь наоборот: источник истины — сам backend. Эти строки он придумывает,
выпуская credentials и решая, кому и до какого момента положен доступ. Наружу они
уходят только в виде готовых VLESS-ссылок и команд агентам.

### customer_entitlements

Корневая строка customer. Все изменения его состояния идут под
`SELECT ... FOR UPDATE` этой строки.

| колонка | тип | что означает |
|---|---|---|
| `customer_id` | `text` PK | непрозрачная строка Customer Service, 1–256 байт |
| `vpn_fleet_id` | `bigint` | флот customer; сменить его в v1 нельзя |
| `expires_at` | `timestamptz` | момент окончания доступа, общий на всего customer |
| `desired_version` | `bigint` | внутренний счётчик изменений состояния; наружу не выдаётся |
| `last_command_number` | `numeric(20,0)` | номер последней применённой команды; команда с номером не больше него игнорируется |
| `created_at`, `updated_at` | `timestamptz` | когда customer заведён и когда состояние менялось |

Пишут: `ApplyCustomerAccess`, `materialize` и `expiry` (`desired_version`).
Читают: `GetCustomerAccessLinks`, `expiry`, `materialize`, `reconcile`, `stats`.

### quota_periods

| колонка | тип | что означает |
|---|---|---|
| `quota_period_id` | `uuid` PK | идентификатор периода; на него ссылаются строки расхода и записи реестра дедупликации |
| `customer_id` | `text` | владелец периода |
| `started_at`, `closed_at` | `timestamptz` | границы; `closed_at IS NULL` ровно у одного, текущего |
| `usage_quota_bytes` | `numeric(20,0)` | квота на каждую ноду отдельно, `> 0` |

Пишут: `ApplyCustomerAccess`.
Читают: `usage`, `GetCustomerAccessLinks`, `reconcile`, `stats`.

Квота лежит здесь, а не в entitlement: она осмысленна только вместе с
потраченным в периоде трафиком. Renewal закрывает текущий период и открывает
следующий.

Периоды — непересекающиеся полуоткрытые интервалы `[started_at, closed_at)`. При
renewal `closed_at` старого совпадает со `started_at` нового с точностью до
значения: разошедшиеся границы означали бы, что дельта трафика не попала ни в
один период.

### node_quota_usage

| колонка | тип | что означает |
|---|---|---|
| `quota_period_id`, `node_id` | `uuid`, `text` | составной первичный ключ |
| `uplink_bytes`, `downlink_bytes` | `numeric(20,0)` | накопленный трафик |
| `total_bytes` | `numeric(20,0)` | генерируемая колонка `uplink + downlink`, хранится (STORED) |
| `exhausted_at` | `timestamptz` | момент исчерпания квоты на ноде; он же признак блокировки |
| `updated_at` | `timestamptz` | когда расход обновлялся последний раз |

Пишут: `ApplyCustomerAccess` и `materialize` (заводят строку), `usage`
(начисление и `exhausted_at`).
Читают: `GetCustomerAccessLinks`, `reconcile`, `stats`.

Трафик всех FREEDOM и BRIDGE access customer на одной ноде идёт в одну строку.
Исчерпание на одной ноде не влияет на доступ на других.

### vpn_accesses

| колонка | тип | что означает |
|---|---|---|
| `access_id` | `uuid` PK | идентификатор доступа; на него ссылаются операции для агента и записи реестра дедупликации |
| `customer_id` | `text` | владелец доступа |
| `kind` | `text` | `FREEDOM` или `BRIDGE` |
| `logical_target_key` | `text` | логическая цель: `node_id` для FREEDOM, `routing_key` для BRIDGE |
| `generation` | `integer` | какой это по счёту доступ к этой цели, с единицы |
| `entry_node_id` | `text` | нода, на которой заводится пользователь |
| `egress_key` | `text` | пустая строка для FREEDOM, тег exit-outbound для BRIDGE; передаётся агенту дословно |
| `accounting_id` | `text` UNIQUE | псевдоним, уходит в Xray как `email` |
| `encrypted_client_uuid` | `bytea` | учётные данные VLESS, AES-256-GCM |
| `encryption_key_id` | `text` | каким ключом зашифровано |
| `desired_state` | `text` | `PRESENT` или `ABSENT` |
| `apply_state` | `text` | `PENDING`, `APPLIED`, `RETRYING`, `FAILED` |
| `desired_version` | `bigint` | версия желаемого состояния |
| `retired_at` | `timestamptz` | момент исчезновения цели из манифеста; у действующих пусто |
| `created_at` | `timestamptz` | когда доступ выпущен |

Читают: `GetCustomerAccessLinks`, `dispatch`, `usage`, `expiry`, `reconcile`,
`stats`. Пишущих шестеро, каждый в свои колонки:

| кто | что меняет |
|---|---|
| `ApplyCustomerAccess` | заводит доступы новому customer, поднимает `desired_state` при renewal |
| `materialize` | заводит доступы на появившиеся цели, проставляет `retired_at` исчезнувшим |
| `expiry` | опускает `desired_state` в `ABSENT` по истечении срока |
| `usage` | опускает `desired_state` в `ABSENT` при исчерпании квоты на ноде |
| `dispatch` | пишет `apply_state` по исходу вызова агента |
| `reconcile` | помечает доступы применёнными по факту принятого полного набора |

Уникальность — `(customer_id, kind, logical_target_key, generation)`. Строка не
удаляется никогда: retired-строки хранят, до какого номера доросло поколение
цели.

## Доставка

### agent_operations

Очередь команд агентам, устроенная как transactional outbox: строка операции
пишется той же транзакцией, что и само изменение `desired_state`. Отсюда
гарантия — не бывает изменения без операции и операции без изменения. Отправкой
занимается отдельный воркер, уже после коммита.

| колонка | тип | что означает |
|---|---|---|
| `operation_id` | `uuid` PK | сохраняется между попытками; по нему агент отсеивает дубли |
| `node_id`, `access_id` | `text`, `uuid` | куда и про какой доступ |
| `operation_type` | `text` | `ENSURE_PRESENT` или `ENSURE_ABSENT` |
| `desired_version` | `bigint` | какую версию желания везёт операция |
| `status` | `text` | `PENDING`, `IN_FLIGHT`, `SUCCEEDED`, `RETRY_WAIT`, `FAILED_PERMANENT`, `SUPERSEDED` |
| `attempt_count`, `next_attempt_at` | `integer`, `timestamptz` | сколько было попыток и когда можно следующую |
| `lease_owner`, `lease_expires_at` | `text`, `timestamptz` | аренда доставки |
| `last_error_code`, `last_error_message` | `text` | чем закончилась последняя попытка |
| `created_at`, `completed_at` | `timestamptz` | когда операция поставлена и когда пришла в терминальный статус |

Пишут: `ApplyCustomerAccess`, `materialize`, `expiry`, `usage` (ставят),
`dispatch` (ведёт), `reconcile` (закрывает ставшие ненужными).
Читают: `stats`.

Уникальность — `(access_id, desired_version)`: повторное планирование того же
изменения второй операции не создаёт.

Полезной нагрузки здесь нет. `client_uuid` и `egress_key` собираются из строки
access перед самым вызовом агента: застрявшая операция иначе везла бы данные,
устаревшие к моменту доставки.

### manifest_materialization_jobs

Раскладка принятого манифеста по всем customer.

| колонка | тип | что означает |
|---|---|---|
| `revision` | `bigint` PK | какую ревизию раскладываем |
| `cursor` | `jsonb` | до какого места дошли; джоба переживает перезапуск, не начиная заново |
| `status` | `text` | `PENDING`, `IN_PROGRESS`, `DONE`, `FAILED` |
| `lease_owner`, `lease_expires_at` | `text`, `timestamptz` | аренда джобы |
| `updated_at` | `timestamptz` | когда джоба продвигалась последний раз |

Пишут: `ApplyFleetManifest` (ставит джобу), `materialize` (ведёт).
Читают: `stats`.

Джоба ставится в транзакции приёма снимка, а исполняется после коммита. Причина в
разнице объёмов: сам снимок это десятки строк топологии, а изменение доступов
затрагивает каждого customer флота, то есть тысячи строк. Держать всё это в
транзакции RPC значило бы отвечать infrastructure pipeline минутами и держать
долгую блокировку.

## Учёт трафика

Xray считает трафик на ноде, но никуда его не отправляет. Забирает его агент и
складывает в **спул** — локальное хранилище на самой ноде (SQLite-база), где
замеры ждут, пока backend их не заберёт и не подтвердит. Пока подтверждения нет,
агент замеры не удаляет: связь с backend может пропасть, а трафик потерять
нельзя.

Внутри спула две единицы, и их не следует путать:

* **item** — одна строка вида «столько-то байт вверх и вниз такому-то
  `accounting_id`»;
* **батч** — порция items, снятая за один заход. Именно у батча есть порядковый
  номер, и подтверждается тоже батч целиком.

Дедупликация при этом идёт по items, а не по батчам: батч мог быть начислен
наполовину, если транзакция упала посередине.

У спула есть идентификатор `spool_id` — случайный UUID, живущий столько же,
сколько сама база агента. Внутри одного `spool_id` батчи пронумерованы подряд.
Если агент пересоздал базу (переустановка, потеря диска), появляется новый
`spool_id`, а нумерация начинается с нуля: сравнивать номера из разных спулов
между собой бессмысленно, и backend этого не делает.

Позиция в спуле — пара `(spool_id, sequence)`, она же курсор.

### node_usage_cursors

Подтверждённая позиция в спуле ноды, она же аренда воркера `usage`.

| колонка | тип | что означает |
|---|---|---|
| `node_id` | `text` PK | нода, чей спул читаем; строка одна на ноду |
| `spool_id` | `text` | идентификатор спула агента; новый `spool_id` сбрасывает нумерацию в ноль |
| `acked_sequence` | `numeric(20,0)` | до какого номера трафик подтверждён; агент удаляет у себя только подтверждённое |
| `lease_owner`, `lease_expires_at` | `text`, `timestamptz` | аренда опроса |
| `updated_at` | `timestamptz` | время последней **попытки** опроса, не последнего сдвига курсора |

Пишут: `usage`.
Читают: `prune-usage-dedup`, `stats`.

Строка заводится лениво, при первом захвате ноды, до всякого успешного опроса.

### traffic_usage_items_processed

Реестр начисленного: пока строка жива, тот же item второй раз не начислится. Вставка идёт через `ON CONFLICT DO NOTHING RETURNING`, отсутствие
результата означает «уже начислено».

| колонка | тип | что означает |
|---|---|---|
| `node_id`, `spool_id`, `sequence`, `accounting_id` | `text`, `text`, `numeric(20,0)`, `text` | составной первичный ключ, он же ключ дедупликации |
| `access_id`, `quota_period_id` | `uuid` | какому доступу и в какой период начислено; пусты для карантинных items |
| `result` | `text` | `APPLIED`, `IGNORED_CLOSED_PERIOD`, `QUARANTINED` |
| `processed_at` | `timestamptz` | когда item обработан; по нему работает ретенция |

Пишут: `usage`, `prune-usage-dedup` (удаляет).
Читают: `stats`.

#### Зачем нужен реестр

Трафик копится у агента в локальном спуле, батчами. Один цикл опроса выглядит
так:

1. Backend вызывает `GetNodeState` и передаёт в запросе свой курсор — позицию, до
   которой трафик уже начислен и закоммичен.
2. Агент удаляет у себя батчи до этой позиции и отдаёт следующие.
3. Backend начисляет полученные батчи и двигает курсор в `node_usage_cursors`.
4. Новое значение курсора уедет агенту **только следующим вызовом**.

Между шагами 3 и 4 есть окно: трафик уже начислен, но агент об этом ещё не знает
и хранит те же батчи у себя. Если backend в этом окне перезапустился, при
следующей встрече агент отдаст их снова. От повторного начисления защищает
реестр: у items этого батча уже есть строки, и вставка через
`ON CONFLICT DO NOTHING` не делает ничего.

#### Почему записи удаляются и почему через 6 часов

Таблица растёт пропорционально трафику: строка на каждого активного пользователя
в каждом батче, а батчи агент отдаёт примерно раз в 15 секунд. Порядка 5760 строк
в сутки на активного пользователя. Без уборки рост неограничен, поэтому она
единственная, из которой строки удаляются.

Ретенция удаляет запись при двух условиях сразу: ей больше 6 часов **и** её батч
уже отмечен подтверждённым в `node_usage_cursors` (либо пришёл из спула, который
агент с тех пор пересоздал — у такого другой `spool_id`, и нумерация в нём
начинается заново). Неподтверждённое не удаляется, сколько бы ни лежало.

Шесть часов — это допустимая длительность простоя backend. Если процесс лежал
дольше, записи о начисленных батчах уже убраны, а агент эти батчи всё ещё хранит,
потому что подтверждения не получил, и отдаст их заново. Трафик начислится второй
раз. Это принятая положительная погрешность учёта: посчитанный расход может
оказаться больше фактического, но не меньше.

### traffic_batch_quarantine

Items, которые не удалось разобрать: неизвестный `accounting_id`, некорректное
содержимое. Один плохой item не должен блокировать батч.

| колонка | тип | что означает |
|---|---|---|
| `quarantine_id` | `uuid` PK | идентификатор записи; генерируется базой |
| `node_id`, `spool_id`, `sequence` | `text`, `text`, `numeric(20,0)` | откуда приехал item |
| `accounting_id` | `text` | может быть пустым |
| `reason` | `text` | почему отвергнут |
| `sanitized_payload` | `jsonb` | очищенное содержимое; сырых секретов здесь нет |
| `created_at` | `timestamptz` | когда item отправлен в карантин |

Пишут: `usage`.
Читают: `stats`.

Рост карантина означает расхождение между тем, кого backend считает заведённым на
ноде, и тем, за кого приходит трафик. Метрика по числу записей годится под alert.

## Аудит

### audit_events

Append-only журнал значимых действий.

| колонка | тип | что означает |
|---|---|---|
| `audit_id` | `uuid` PK | идентификатор записи; генерируется базой |
| `occurred_at` | `timestamptz` | когда действие произошло |
| `actor_type`, `actor_id` | `text` | `SYSTEM`, `MANIFEST_WRITER` или `CUSTOMER_ACCESS_WRITER` |
| `action` | `text` | `MANIFEST_APPLIED`, `CUSTOMER_CREATED`, `CUSTOMER_RENEWED`, `CUSTOMER_QUOTA_CHANGED`, `CUSTOMER_EXPIRED` |
| `target_type`, `target_id` | `text` | `MANIFEST_REVISION` или `CUSTOMER` |
| `request_id` | `text` | сквозной идентификатор запроса; связывает запись с логами вызова |
| `outcome` | `text` | исход действия |
| `sanitized_metadata` | `jsonb` | без секретов |

Пишут: `ApplyCustomerAccess`, `ApplyFleetManifest`, `expiry`.
Читают: никто.

Запись идёт в той же транзакции, что и само действие. Backend эту таблицу не

нет. Значения полей — `SCREAMING_SNAKE_CASE`, перечислены в
`internal/app/audit.go`.

## Инварианты, которые держит сама база

Проверка в коде читает закоммиченный снимок и гонку не ловит, поэтому часть
правил вынесена в схему.

| индекс | инвариант |
|---|---|
| `agent_operations_single_in_flight_per_node` | одна операция в полёте на ноду; частичный по `status = 'IN_FLIGHT'` |
| `quota_periods_one_open_per_customer` | один открытый период квоты на customer; частичный по `closed_at IS NULL` |
| `vpn_accesses_current_target` | один действующий доступ на логическую цель; частичный по `retired_at IS NULL` |
| `vpn_bridge_routes_current_pair` | одна действующая пара entry → exit во флоте |
| `vpn_accesses.accounting_id` | глобальная уникальность псевдонима |

Проигранная гонка опознаётся по имени constraint'а.

Отдельно стоит уникальность `accounting_id`: при её нарушении транзакция обязана
упасть, а не сгенерировать значение заново. Значение состоит из 20 символов
base32, то есть 100 бит от системного CSPRNG, и случайное совпадение двух таких
значений практически невозможно. Если совпадение всё же произошло, объяснение
одно: генератор случайных чисел выдаёт повторяющиеся байты. Из того же генератора
(`crypto.Generator`, один `io.Reader` на все значения) берётся `client_uuid` —
учётные данные VLESS. Молчаливый повтор генерации по конфликту скрыл бы поломку и
продолжил выпускать предсказуемые credentials.

## Локальная база

```bash
make dev           # PostgreSQL на порту 5433 (tmpfs) и накатить схему
make dev-db-down   # остановить и удалить данные
```

Порт 5433 и tmpfs выбраны намеренно: интеграционные тесты делают `TRUNCATE` всех
таблиц перед каждым тестом, и эта база должна быть заведомо одноразовой.
