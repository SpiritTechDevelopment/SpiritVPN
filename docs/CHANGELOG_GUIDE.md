# Руководство по CHANGELOG

## Назначение

Файл `CHANGELOG.md` используется для фиксации значимых изменений в SpiritVPN по версиям и поддерживается в формате **Keep a Changelog** с использованием **Semantic Versioning**.

## Общая структура

Рекомендуемый формат:

```markdown
## [Unreleased]

### Добавлено
- Описание новой функциональности

### Изменено
- Описание изменения существующего поведения

### Исправлено
- Описание исправления

### Удалено
- Описание удаленной функциональности

### Breaking Changes
- Описание несовместимых изменений
```

## Правила ведения CHANGELOG

1. Вносите только значимые для пользователей и разработчиков изменения
2. Используйте краткие и точные формулировки
3. Группируйте записи по типу изменений
4. Не включайте в CHANGELOG несущественные внутренние правки без влияния на поведение, API, документацию или эксплуатацию
5. Поддерживайте единый стиль формулировок в одном времени и одном языке

## Категории изменений

### Добавлено

Новая функциональность, новые модули, новые эндпоинты, новые сценарии конфигурации или интеграции.

### Изменено

Изменение поведения существующих компонентов, формата конфигурации, логики логирования, структуры данных или процесса эксплуатации.

### Исправлено

Исправления ошибок, регрессий, дефектов интеграции и проблем совместимости.

### Удалено

Удаленные возможности, устаревшие механизмы или исключенные зависимости.

### Breaking Changes

Изменения, нарушающие обратную совместимость.

## Процесс обновления

### При разработке

Изменения вносятся в секцию `Unreleased` до релиза.

Пример:

```markdown
## [Unreleased]

### Добавлено
- Добавлен worker сбора статистики трафика

### Исправлено
- Исправлена обработка ошибок в пакете logger
```

### При выпуске релиза

1. Создайте новую секцию с номером версии и датой
2. Переместите записи из `Unreleased` в новую секцию
3. Обновите ссылки внизу файла
4. Создайте Git tag
5. Подготовьте релиз на GitHub на основе соответствующей секции CHANGELOG

Пример:

```markdown
## [Unreleased]

## [0.2.0] - 2026-02-01

### Добавлено
- Добавлен worker сбора статистики трафика
```

## Семантическое версионирование

Используйте следующие правила изменения версии:

* **MAJOR** — несовместимые изменения
* **MINOR** — новая функциональность без нарушения обратной совместимости
* **PATCH** — исправления ошибок без нарушения обратной совместимости

## Рекомендации по формулировкам

Используйте официальный, краткий и нейтральный стиль.

Рекомендуется:

* начинать запись с глагола в прошедшем времени;
* указывать предмет изменения без избыточных деталей;
* при необходимости добавлять номер PR или автора.

Примеры:

```markdown
### Добавлено
- Добавлен health check эндпоинт API (#19)
- Добавлен worker сбора статистики трафика (#18)

### Изменено
- Обновлена конфигурация Telegram hook для логгера

### Исправлено
- Исправлены import paths в примерах
```

## Автоматизация

Если в репозитории используется CI/CD-автоматизация для поддержки CHANGELOG, она должна дополнять, а не заменять ручную проверку содержимого перед релизом.

Перед публикацией релиза рекомендуется убедиться, что:

* записи находятся в корректных категориях;
* формулировки не дублируются;
* ссылки на версии и теги обновлены;
* содержимое соответствует фактическому состоянию репозитория.

## Практические рекомендации

1. Обновляйте `CHANGELOG.md` одновременно с изменением кода
2. Не смешивайте разные типы изменений в одной записи
3. Поддерживайте единый словарь терминов по всему проекту
4. Используйте одинаковый формат дат и номеров версий
5. Проверяйте CHANGELOG перед созданием тега и GitHub Release
